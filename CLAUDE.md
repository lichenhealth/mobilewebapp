# Lichen — PWA project guide

Lichen is a holistic-healing nonprofit + conscious-economy platform. This repo
(`lichenhealth/mobilewebapp`, package `lichen-pwa`) is the member-facing PWA.
The founder is non-technical; explain reasoning briefly and prefer small,
reviewable changes. Keep Plan Mode on for anything touching the database or auth.

## Stack & deploy

## Conventions
- Design tokens live in `src/styles/tokens.css` (peach accent `--peach`, bone canvas, Archivo body, display serif). Reuse token vars; match existing BEM-ish class names (`.onb__`, `.prof__`, `.cat__`, `.adminc__`, `.conv-row`, `.thread__`).
- Logo: `src/components/LichenMark.tsx`. Icons: `src/components/Icon.tsx` (top-bar section marks force 1.2px hairline strokes via vector-effect: non-scaling-stroke — PR #100; icons' native strokeWidths are tuned for SMALL sizes) (`<Icon name=... size=... />`).
- Avoid the word "spaces" in member-facing UI — say organizations / communities / groups / places.
- Supabase embeds: when a table has >1 FK to another, disambiguate with the explicit hint, e.g. `profiles!subscriptions_profile_id_fkey(full_name)`. SELF-referencing FKs (spaces.parent_space_id): do NOT embed at all — the FK-NAME hint fails outright ('could not find a relationship between spaces and spaces', PR #57) and the COLUMN hint `spaces!parent_space_id(...)` PARSES but resolves to the CHILDREN direction (an array — rendered ghost 'part of' labels until PR #59). Fetch the parent row explicitly by parent_space_id instead (see spacesApi loadSpaceProfile/listSpacesByKind).
- React hooks must ALL sit above any early return (`if (loading) return …`). A hook added below one crashes the whole app to a blank page when the data arrives ("Rendered more hooks…") — this took out every event page in prod until PR #46 (2026-07-05).
- New enum values can't be USED in the same migration that adds them — add in a separate step that's committed first.
- Only 3 columns use real Postgres enums (`account_capability`, `space_kind`, `space_member_role`). The other "enum-like" fields below (care `status`, subscription `tier`/`source`, category `domain`, suggestion `status`) are actually `text` columns with CHECK constraints — to add a value, change the CHECK, not an enum type.

## Data model (all RLS-enabled)
- `profiles` (id→auth.users; full_name, headline, bio, email, onboarded, is_admin). Trigger creates a profile on signup.
- `profile_capabilities` (service_provider / goods_provider).
- `categories` (63 seeded; text slug id, domain good|service, name, sort) + `profile_categories`. Member-suggested categories via `category_suggestions` + admin approval RPCs `approve_category_suggestion` / `reject_category_suggestion`.
- `spaces` (kind enum: organization|community|group|place; created_by; `parent_space_id` — groups NEST under communities/orgs, nullable = standalone) + `space_members` (role enum: super_admin|admin|member). Creator becomes super_admin via trigger `handle_new_space`. One super_admin per space. MEMBERSHIP IS REQUEST+APPROVAL (2026-07-14, PR #56, migration `20260719120000_space_nesting_requests.sql`): `space_membership_requests` (care-team shape — initiated_by=self → join request admins approve via `approve_join_request()`; =admin → invite accepted via `accept_space_invite()`); STANDALONE GROUP CREATION lives on /groups too (PR #96, 2026-07-17 — New group button; founder: groups must not REQUIRE a community). NESTING IS CONSENSUAL: `space_nesting_requests` (group admins propose via the Part-of picker or anyone via 'Propose a group' — group is created standalone immediately; parent admins approve via `approve_group_nesting()` or Release later via `eject_group()`; `enforce_parent_consent` trigger blocks non-consensual parent writes). MEMBER SUGGESTIONS (2026-07-14, PR #58, migration `20260720120000_member_suggestions.sql`): any MEMBER may insert a request row for someone else = a SUGGESTION (third INSERT-policy arm); trigger notifies admins only (suggested person hears nothing); admins endorse via `endorse_member_suggestion()` (row's initiated_by becomes the admin → real invite, person notified); `accept_space_invite()` requires the initiator be an admin (a bare suggestion can't be self-accepted). SpaceProfile + circle = an ADD MENU (Post / Marketplace listing / Event via Compose presets / New group (admins) / Propose a group); Members section type-ahead: admins Invite, members Suggest; icons: 'member-heart' (Members) + 'groups' (Groups mark from the Figma icon set). All flows notify via `notify()` (section 'home', space-scoped). Roles are strictly per-space.
- `chats` (one per space — all kinds — and one per care team) + `chat_members` (synced to space_members via trigger) + `chat_messages` (realtime enabled). RLS uses `is_chat_member()` helper to avoid recursion.
- `care_team_members` (patient_id, caregiver_id, status pending|active, initiated_by). Either party initiates; the OTHER approves. Activation trigger creates/join the care-team chat.
- `care_invitations` (invite non-members by email; `claim_care_invitations()` RPC converts them to pending care links on signup).
- `subscriptions` (tier community|concierge, source gift|stripe, status active|past_due|canceled, current_period_end — gifts reuse it for their end date). Admin RPCs `gift_subscription(email, tier, months?)` / `revoke_subscription`. `membership_gifts` (PR #67): pending gifts keyed to an invitee's EMAIL, claimed at signup by `claim_membership_gift()` (called from the App gate; on-conflict-do-nothing never clobbers a paid sub). `chat_members.last_read_at` = per-member chat read cursor (PR #67).

## Real-data architecture (design locked 2026-06-30 — the next major build)
Turning the mock feed/marketplace/mycelium into a real platform. Cornerstone decisions:
- **Members are ENTITIES, not just people.** An entity has a `kind` (person / plant / animal / place / organization). Humans log in; non-humans (e.g. *Tango* the therapy horse, a *San Pedro* cactus) are **stewarded** by a human and act through them. Contributions and value accrue to the *entity itself* (the conscious-economy ledger — a cross-species economy). Today `profiles` = humans (auth-linked). Generalizing `profiles` into multi-species entities (add `kind` + `steward_id`, allow non-auth profiles) is a foundational step; `posts`/`mycelium` are designed to absorb it (an author stays a profile row that *becomes* an entity).
