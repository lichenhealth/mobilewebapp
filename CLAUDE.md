# Lichen — PWA project guide

Lichen is a holistic-healing nonprofit + conscious-economy platform. This repo
(`lichenhealth/mobilewebapp`, package `lichen-pwa`) is the member-facing PWA.
The founder is non-technical; explain reasoning briefly and prefer small,
reviewable changes. Keep Plan Mode on for anything touching the database or auth.

For the dated, PR-by-PR story of how any of this got built — the "why" behind
a non-obvious decision — see [`docs/HISTORY.md`](docs/HISTORY.md). This file
is the current-state reference only.

## Stack & deploy
- React 18 + Vite + TypeScript. Build: `tsc -b && vite build` (it type-checks — always run before considering a change done, and fix all errors; the project builds clean).
- No package-lock; Vercel runs `npm install`. Vercel auto-deploys `main` on push.
- Backend: Supabase (project `mjqnaevertyzgjlpwynr`). Anon key is hardcoded in `src/lib/supabase.ts` (public by design; RLS protects data).
- DB schema is version-controlled in `supabase/migrations/00000000000000_init.sql` — a `pg_dump --schema-only --schema=public` baseline plus a manually-appended `auth.users` signup trigger. It's a record/backup, not auto-applied — the live schema is edited in the Supabase dashboard and this file can drift; refresh it after DB changes. Supabase CLI is linked (`supabase/config.toml`); `pg_dump` lives at `/opt/homebrew/opt/libpq/bin/pg_dump` (no Docker). `supabase db dump`/`db pull` need Docker, which isn't installed — use the direct `pg_dump` against the session pooler instead.
- Migrations can run directly: `worker/migrate.sh <file>` applies a migration via `psql` (`/opt/homebrew/opt/libpq/bin/psql`) using `SUPABASE_DB_URL` from the gitignored `worker/.env` (session-pooler URI, founder-supplied, never passes through chat). Runs as one transaction (`ON_ERROR_STOP` + `psql -1`) — a failure rolls back cleanly. Routine additive migrations can run directly and get reported after; anything destructive (dropping a column, deleting rows, rewriting existing data) needs the founder's explicit yes first.

### Domains & email
- `lichen.health` **is the app** — canonical origin (`APP_ORIGIN` in `src/lib/customDomain.ts`, `APP_URL` edge secret). `lichen.healthcare` (+www, and www.lichen.health) 308-redirects every path to the same path on `lichen.health` via `vercel.json` host-matched rules. ⚠ `/:path*` does **not** match the bare root on host rules — explicit `source: "/"` rules exist for each host; keep both when adding a new host.
- DNS: `lichen.health` stays on **Wix** nameservers (A record → Vercel). **Google-Workspace MX for `connect@lichen.health` lives there — never touch.** Transactional email still sends **from** `lichen.healthcare` (Resend MX; deliberate, invisible to members).
- Signed-out `/` on `lichen.health` serves the static Astro marketing homepage (`public/welcome/` — filesystem-first, shadows the SPA rewrite; bounces to `/home` via a localStorage auth-token check for signed-in browsers). `/get-involved`, `/founders-circle`, `/project/*` also ship static. The app itself keeps richer in-app versions of `/about /donate /blog /resources` + essay slugs. PWA manifest `start_url` = `/home` (installed apps skip the marketing shell).
- The old marketing site's long-form content (11 founding essays + 6 reading lists) lives **in the app** as public Library posts (`'The Lichen essays'` / `'The Lichen bookshelf'` collections, fixed uuid5 ids); legacy slugs (`/mission /ourstory /blog /resources` etc.) redirect in `App.tsx`. Anon users can read public posts + published collections (signed-out browsing is deliberate — the growth loop).
- To edit a static marketing page: edit the `lichenhealth/lichen-health` repo (Astro) → `npm run build` → copy the built page dirs + `_astro` into this repo's `public/` (re-inject the `welcome/index.html` auth-bounce script — it's hand-patched, not part of the Astro build) → push **both** repos.

### Local verification with a test account
There's one live Supabase project (no separate staging), so "local" verification means the local Vite dev server against the real database, signed in as a dedicated, low-stakes account (`galyn+claudetest@lichen.health`, profile name "Claude Test", gifted a Community subscription) — never the founder's real one. Claude does not type a password into a login form or call `signInWithPassword` itself, even for this throwaway account — that's a hard rule, not a preference.

**Getting a session (no founder involvement needed):** `worker/mint-test-session.sh [email]` mints a fresh session server-side via Supabase's Admin Auth API (`generate_link` → `verify`) using the service-role key already in `worker/.env`, and writes it to `worker/test-session.json` (gitignored — same trust boundary as `worker/.env`). Standing Bash permission rule already covers running it, no approval prompt. Claude then injects the contents into the Browser-pane preview via `localStorage.setItem('sb-mjqnaevertyzgjlpwynr-auth-token', <contents>)` + reload.

Fallback (only if the account doesn't exist yet, or the service-role key isn't available): the founder signs into the account once in their own browser, opens devtools → Application → Local Storage, and copies the `sb-mjqnaevertyzgjlpwynr-auth-token` value into `worker/test-session.json` by hand.

**Standing protocol (founder, 2026-08-09): test before declaring UI work done.** For any UI/frontend push, sign in as the test account and actually click through the changed flow at both mobile and desktop widths in the Browser pane — not just a code read or a single screenshot — before reporting complete. Fix whatever's found, re-verify, then report. This is load-bearing, not optional polish; it's already caught real bugs (a popover-overlap and an off-screen-clipping bug) that a code read alone missed.

## Conventions
- Design tokens live in `src/styles/tokens.css` (peach accent `--peach`, blue `--blue` for admin/stewardship affordances, green `--green` for availability/free, bone canvas, Archivo body, display serif). Reuse token vars; match existing BEM-ish class names (`.onb__`, `.prof__`, `.cat__`, `.adminc__`, `.conv-row`, `.thread__`).
- Logo: `src/components/LichenMark.tsx`. Icons: `src/components/Icon.tsx` (`<Icon name=... size=... />`; top-bar section marks force 1.2px hairline strokes via `vector-effect: non-scaling-stroke` — native strokeWidths are tuned for small sizes).
- Avoid the word "spaces" in member-facing UI — say organizations / communities / groups / places.
- Supabase embeds: when a table has >1 FK to another, disambiguate with the explicit hint, e.g. `profiles!subscriptions_profile_id_fkey(full_name)`. SELF-referencing FKs (`spaces.parent_space_id`): do **not** embed at all — the FK-NAME hint fails outright and the COLUMN hint `spaces!parent_space_id(...)` parses but resolves to the CHILDREN direction (an array). Fetch the parent row explicitly by `parent_space_id` instead (see `spacesApi` `loadSpaceProfile`/`listSpacesByKind`).
- React hooks must ALL sit above any early return (`if (loading) return …`). A hook added below one crashes the whole app to a blank page when the data arrives ("Rendered more hooks…").
- New enum values can't be USED in the same migration that adds them — add in a separate step that's committed first.
- Only 3 columns use real Postgres enums (`account_capability`, `space_kind`, `space_member_role`). Other "enum-like" fields (care `status`, subscription `tier`/`source`, category `domain`, suggestion `status`) are actually `text` columns with CHECK constraints — to add a value, change the CHECK, not an enum type.
- RLS policies must never reference each other in a cycle (42P17 recursion) — route through a `SECURITY DEFINER` helper instead (`is_chat_member()`, `is_event_attendee()`, `owns_reminder()`, `is_space_admin()` are the existing examples; reuse the pattern for any new two-tables-reference-each-other case — including hand-rolled duplicates of an existing helper, which sit on the same latent-cycle shape even before they've actually recursed).
- Migrations pasted through the Supabase dashboard need a **named** dollar-quote tag (`$func$`, not `$$`) — the dashboard's paste can mangle a bare `$$` into `$` (42601).
- `.app-shell` must stay `overflow-x: clip`, never `hidden` — `hidden` silently kills `position: sticky` app-wide.
- `.h-scroll`'s own 12px gap beats a row's own `gap` — new horizontally-scrolling rows need a double-class selector (`.icon-row.h-scroll` etc.) to override it.
- `tokens.css`'s `--wall-gutter` is applied globally via `.scroll-view`'s `padding-inline` — a mandatory minimum side indent even when a section forgets its own padding. Full-bleed screens (chat thread, auth, maps, about, guest pages) opt out via an explicit inline `padding: 0` in `App.tsx`.
- `\u` escapes do not process inside JSX attribute strings — write the literal character in placeholder text, not the escape sequence.
- A recurring class of bug: a shared row's own back-chip/back-button styling loses an import-order specificity tie against a page-specific override. Fix with a compound selector (e.g. `.cmp__back.postp__back`), never a bare rule.
- `loadFeed()` is the shared source for Events/Marketplace/AreaFeed/Maps/search — any filter added there needs to be **opt-in** (a flag like `{ river: true }`), not applied by default, or it silently drops posts from every other surface that calls it. Same pattern: Compose's "Skip the feed" writes `details.quiet`, honored only where `river: true` is passed.
- Consent bubbles (`ConsentBubble.tsx`) are the pattern for a setting that needs in-context explanation (presence, findability): anchored to the control it governs, an "Edit `<setting>`" door, only one visible at a time, seen-state tracked per **member** via `member_prompts` (not per device — a new phone isn't a changed mind, so don't re-prompt on it).
- `MemberRow.tsx` is the one shared row for every member/space listing (Home Directory, My-celium's web, a space's Members tab) — avatar, shield-or-thumb (person→trust, space→recommend), weave mark, labeled Message door. `chatApi.ts` exports `CLAUDE_PROFILE_ID` (the single source — don't re-inline the UUID), `sortClaudeFirst()`, and `hasDirectChatWith()` (a read-only existence check on `chats.direct_key`, unlike `ensureDirectChat` which creates the row). Claude's avatar look (Si-blue circle, brain glyph) lives in `public/claude-avatar.svg`, referenced by `profiles.avatar_url` — recolor by editing that file, not in code.
- Desktop responsiveness (`@media (min-width: 1024px)`, matching the app-shell's own sidebar breakpoint) was historically added screen-by-screen, not systematically — a 2026-08-09 sweep applied two reusable idioms uniformly: row/tile lists go `grid-template-columns: repeat(auto-fill, minmax(Npx,1fr))` (`ListingTile.css`'s `.tile-grid` is the original), FeedCard stacks (Home/My-celium/AreaFeed's feed view/Saved) use the same idiom at `minmax(360px,1fr)`. `.prof` (shared by `Profile.tsx` and `SpaceProfile.tsx`) was hard-capped at the literal mobile width (`--app-max`, 430px) even inside the desktop column — fixed via a `SpaceProfile`-only `is-space` modifier class widening to 720px, leaving `Profile.tsx`'s genuinely-narrow settings page untouched. Chat/ChatThread desktop split-view was explicitly deferred — `ChatThread.css`'s `.thread` is a full-viewport fixed overlay and no split/master-detail pattern exists anywhere in the codebase; making it desktop-native is new UX design work, not a CSS gap.

## Data model (all RLS-enabled)

### Identity & profiles
- `profiles` (id→auth.users; `full_name` [kept in sync from `first_name`/`last_name` by trigger `compose_full_name` — never write `full_name` client-side], `headline`, `bio`, `email`/`phone` [**not** in the column-scoped SELECT grant — owner reads via session/`my_phone()`, others never see them directly; care team reads phone via `on_call_roster()`], `onboarded`, `is_admin`, `identity_tags` text[] [public], `home_location`/`home_lat`/`home_lng`/`home_area` [not granted — owner via `my_home()`, viewers via `mappable_members()`], `presence_visible`/`presence_lit_until`/`presence_always_present`, `timezone`, `findable` [default true], `assistant_readable` [default true], `page` jsonb [public-page template content], `contact` jsonb, `public_page` bool [default **false** for people], `handle`). Trigger creates a profile on signup.
- `can_see_profile()` gates profile reads (replaced a blanket `USING (true)`): visible if `findable=true`, OR you share a space/chat/care-team/web edge with them, OR you're reading one of their public posts (a feed has to be able to name its author). Because that last arm can't be replicated in a plain client query, Directory/people-search/type-aheads additionally filter `findable` themselves.
- `profile_capabilities` (service_provider / goods_provider). `financial_positions` (pk profile_id; income_band CHECK, household_size, circumstances; RLS = owner-all + active care-team SELECT-only — never a score, never shown to anyone else).
- `categories` (3 domains: good / service / place; text slug id, name, sort, `section` healing|everyday) + `profile_categories`. Member-suggested via `category_suggestions` + admin RPCs `approve_category_suggestion()` / `reject_category_suggestion()`.

### Spaces & membership
- `spaces` (kind enum organization|community|group|place; `created_by`; `parent_space_id` — groups nest under communities/orgs, nullable = standalone; `handle` — routes `/:handle`; `lat`/`lng`; `contact`/`page` jsonb; `public_page` [default true for org/place, false for community/group — enforced by the `set_space_public_page_default()` BEFORE INSERT trigger, since a column DEFAULT can't reference another column of the same row; the page-BUILDER itself, `PageTabsEditor`, is unconditional for all four kinds, only this default differs]; `cohort_of` [→ collections, when this space is a course cohort], `term`) + `space_members` (role enum super_admin|admin|member; `duties` text[] — null = full admin, v1 keys `library`/`courses`/`members`). Creator becomes super_admin via `handle_new_space` trigger; one super_admin per space. `set_member_role()` is the only door for granting/scoping roles (super-admin-only).
- Membership is **request + approval**: `space_membership_requests` (`initiated_by=self` → admin approves via `approve_join_request()`; `initiated_by=admin` → invitee accepts via `accept_space_invite()`, which requires the initiator be an admin — a bare member suggestion can't self-accept). A third INSERT-policy arm lets any member file a *suggestion* for someone else; admins turn it into a real invite via `endorse_member_suggestion()`.
- Nesting is **consensual**: `space_nesting_requests` (a group is created standalone immediately; parent admins approve via `approve_group_nesting()` or release later via `eject_group()`; trigger `enforce_parent_consent` blocks non-consensual parent writes).
- `space_section_shares` (pk space+post+area; pending/approved/declined) — a space's Courses/Library sections show only space-authored posts plus duty-approved member shares; `decide_section_share()` RPC.

### Chat
- `chats` (kind organization|community|group|place|care_team|direct|event|help) + `chat_members` (synced from `space_members` via trigger; `last_read_at` = per-member read cursor) + `chat_messages` (realtime enabled). RLS goes through the `is_chat_member()` helper to avoid recursion. `ensure_direct_chat()` for 1:1 DMs. `mark_chat_read(chat)` bumps the cursor and clears that chat's notifications. `chat_unread_counts()` RPC powers inbox pills.
- `profiles.assistant_readable` gates whether **other members'** assistants can read your message *content* in a cross-chat briefing — your own assistant always sees your messages; the fact you wrote (not the content) still counts for someone whose flag is off.

### Care
- `care_team_members` (patient_id, caregiver_id, status pending|active, initiated_by — either party can initiate via `offerCareFor()`, the other approves; activation creates/joins the care-team chat). `care_invitations` (email invites for non-members; `claim_care_invitations()` on signup). `care_posts` (WOW 0–100 scores + Kindnesses-of-Care recurring board). `on_call_roster(patient)` (SECURITY DEFINER — gated to the patient or a fellow active caregiver).

### Membership & subscriptions
- `subscriptions` (tier community|concierge, source gift|stripe, status active|past_due|canceled, `current_period_end` — gifts reuse it as their end date). Admin RPCs `gift_subscription(email, tier, months?)` / `revoke_subscription()`. `membership_gifts` — pending gifts keyed to an invitee's email, claimed at signup via `claim_membership_gift()` (on-conflict-do-nothing, never clobbers a paid sub). `grant_growth_gift()` — every member gets one 3-month Concierge gift automatically (self, on-conflict-do-nothing so it's truly once); called from the App gate right before it would redirect to `/membership`.
- Membership gate (`App.tsx`, session-cached ref): signed-in + onboarded + non-admin needs an active/past_due subscription or a live gift, else → `/membership`. `GATE_EXEMPT` = auth flows + `/membership` + `/help` + `/donate` + `/privacy` + `/terms` + `/about`. Admins always bypass. Signed-out visitors can still browse public content.

### Content, posts & marketplace
- `posts`: author, optional `space_id`, `audience_space_ids`, `visibility`, `content_type` (`social` / `actionable` drive the live UI split — Compose's two big face cards; `creative`/`educational`/`qa` persist on old posts only, no longer chosen at creation), `service_areas[]` (marketplace/work/courses/food/art/events/places/library/travel), `details` jsonb (area-specific: `modes[]`/`mode` [primary], `price`, `condition`, `availFrom`/`availTo`, `fulfillment`, `deliverRadiusMi`, `paymentPlan`, `tradeTags`, `categories[]`, `location`/`geo`, `meetingUrl`, `online`/`inPerson`, `quiet`, `demo`, `styleTags`, `giftTo`, `modeNotes`, `allocation`, `modules` [course lesson groups]).
- Marketplace modes are **multi-select**: gift, trade, rent, lend, borrow, sliding-scale, sale, plus ISO ("in search of," demand-side). `details.modes` = everything selected; `details.mode` = primary by precedence `lichen > gift > trade > lend > rent > borrow > iso > paid`. **Lichen\*** ("entrusted offering") is exclusive — selecting it hands allocation to Lichen's Routing Desk (`/admin/supporters` → RoutingDesk.tsx: scores entrusted offerings against open ISOs, steward acts on the top matches; human-in-the-loop v1 of a future autonomous router). `inkind_donations` covers tax-deductible in-kind gifts *to Lichen itself* (distinct from a Lichen\* marketplace listing).
- A trigger (`match_marketplace_post()`, AFTER INSERT on `posts`) is the deterministic ISO matcher: a new public offer/ISO bells matching open ISOs/offers on stemmed-lexeme title+body overlap, 90-day window.
- `hidden_posts` (owner-only, no FK — hides survive post deletion) + `saved_items` (polymorphic, strictly owner-only RLS — no counts or signals visible to anyone, including the author).
- `style-tags` edge function (Claude vision, a controlled ~40-word vocabulary) tags marketplace photos into `details.styleTags` on publish — fire-and-forget, never blocks the post. `listing-autofill` edge function suggests category/condition/tradeTags from title+body text (Compose's "✨ Suggest details" button; pre-checked chips the member can uncheck).
- Trust vs Recommend (current design): **trust is person-to-person only and private** — no shield anywhere on orgs/groups/communities/places, only on people. **Recommend** is available on any entity or post and is the public amplify signal. Mycelium ("your web") = plain membership; vouching = trust, a separate boolean that auto-adds to your web (unvouching withdraws trust but leaves any recommendations). The endorsement overlay everywhere is a query: `(endorsers of item) ∩ (your mycelium)` — always "what my web endorses," never a global score. No counts or leaderboards anywhere, by design. `mycelium.vouched=true` is structurally blocked for `target_type='space'` (a CHECK constraint, not just UI omission). Its SELECT RLS is locked to your own rows (`truster_id = auth.uid()`) — the 2-hop "trusted by someone I trust" check reads anyone else's edges only via `trust_edges_for_targets()`, a `SECURITY DEFINER` RPC scoped to specific targets already in view (a search result, a listing's seller), never a whole-graph read. `src/lib/trustPath.ts`'s `loadTrustEdgesFor()` is the client wrapper — merge its result into a `TrustWeb`'s `edges` before calling `trustPathTo()`.
- Home and My-celium both lead their icon row with a lit **Feed** door; the old ALL/SOCIAL/ACTIONABLE tabs were retired — `content_type` stays in the DB (drives Compose's actionable/social split, the marketplace auto-add, and the ISO matcher) but no longer filters the feed.
- Demo/seed content (a small cast of example members + spaces, see `supabase/demo_content.sql` / `demo_cast.sql`) is marked `details.demo=true` and renders a dismissible EXAMPLE bubble (`.ex-bubble`) on FeedCard/ListingTile/ListingRow; hides via the normal `hidden_posts` mechanism. A one-block wipe SQL sits at the bottom of `demo_cast.sql` for when alpha content needs clearing.
- Card renderers: `FeedCard.tsx` (stream view), `ListingTile.tsx` (grid/browse view — square photo tiles, typographic covers for text-only listings), `ListingRow.tsx` (job-board rows, used by Work). `AreaFeed.tsx` is the generic area-scoped feed component (`area` prop) powering Marketplace/Courses/Library/Art/Work/Food/Travel.

### Collections, courses & library
- `collections` (owner, name, description, `is_public`, `space_id` [space-owned], `kind` `'collection'|'course'|'path'` [`'path'` displays as "Ordered collection" — DB value unchanged], `details` jsonb — level/format/length/forWhom/price/coverUrl/`modules`). `collection_items` (polymorphic target, `position` = order). `collection_enrollments` + `collection_progress` (learner-private RLS). `collection_suggestions` (member-submitted pieces; `resolve_collection_suggestion()`).
- A **cohort** is a `spaces` row of kind `group` tagged `cohort_of` → a course/path collection, with a `term` — not a new `space_kind`. Each cohort is a real group (its own chat/calendar/consent flow); a course can have many cohorts over time.

### Presence
- `profiles.presence_visible` (default **true**, opt-out) drives the "around" dot when active. `presence_always_present` drives the "present" 🕯️ candle (a persistent TopBar toggle, no auto-fade). `network_awake_count()`/`network_awake_list()` are SECURITY DEFINER aggregates (population ∩ opted-in members; no timestamps, no per-individual read grant — presence is a gift, never a status). Space-level awake counts include yourself.

### Resources (bookable rooms/things)
- `resources` (one-owner CHECK: `space_id` XOR `owner_profile_id`; kind room|thing; bookable; approval request|instant) + `resource_bookings` (parties-only read RLS, no client writes). RPCs: `request_resource_booking`, `decide_resource_booking`, `cancel_resource_booking`. `events.owner_resource_id` widened the one-owner CHECK to profile|space|resource — a resource has its own calendar. `resource_busy()`/`resource_span_contact()` expose free/busy without leaking who booked what; a booker can be messaged only through the deliberate contact door.

### Calendar, events & bookings
- Shared recurrence engine (`src/lib/recurrence.ts`, RRULE-lite + `occursOn()`) powers calendar events, reminders, and the `fire-reminders` edge function alike.
- `calendar_shares` (audience rules, most-specific-wins) + `free_busy()`/`availability_of()` RPCs. `external_calendars` (ICS import via the `sync-external-calendar` edge fn) + `calendar_shares.external_calendar_id` — an imported calendar's visibility is capped at busy-only unless it explicitly opts into `share_titles`.
- An event = a `posts` row (`content_type='actionable'`, `service_areas ⊇ ['events']`) linked via `posts.linked_event_id` to a real `events` row. RSVP = `event_attendees` (going/tentative/declined), gated through `is_event_attendee()` (SECURITY DEFINER — the reusable pattern for any RLS cycle between two tables that reference each other). Event chat (`chats.kind='event'`) syncs its roster via the `sync_attendee_to_event_chat` trigger. Host edits always go through `updateEventDetails()` — never `updateEvent()`, whose invitee-sync wipes RSVPs.
- `reminders` (private, owner + shared via `reminder_recipients` type-ahead) + `reminder_done` (keyed per reminder+profile+date — each recipient ticks their own occurrence) + `reminder_fired` (cron dedup claim). `notify_reminder()` bells recipients. Reminders are **never** busy and never appear in free/busy.
- Bookings (the Calendly-style layer): `booking_types` (audience everyone|mycelium; approval request|instant) + `bookings`, all writes through SECURITY DEFINER RPCs (`booking_board`, `create_booking` — server revalidates window containment, overlap, and buffer). No payments yet.
- `event_guests` — invite people outside Lichen to an event (`send-event-invite` edge fn mints an unguessable token); `guest_event(token)`/`guest_rsvp(token, status)` RPCs are granted to `anon`.
- Scheduled reminders run on `pg_cron` (`tick_reminders()` every minute) + `pg_net` → the `fire-reminders` edge function, using each recipient's `profiles.timezone`. `push_subscriptions` + the `send-push` edge function deliver web push, triggered by a `pg_net` trigger on `notifications` INSERT — push rides the existing `notify()` call for everything (nudges, DMs, gifts, reminders, all of it), no per-feature wiring needed.

### Current-cy ledger
- `ledger_entries` (append-only — a trigger refuses UPDATE/DELETE; corrections are offsetting `'adjustment'` entries; polymorphic parties profile|space, designed to extend to non-human entities without a schema change). No INSERT policy — writes only via `send_currentcy()` (self or an admined space, advisory-lock race-safe) and `mint_currentcy()` (admin-only issuance). `ledger_balance()` refuses to reveal anyone else's balance — no leaderboards, by construction, same anti-gamification stance as trust. Architecture: transparent DB ledger + a $1 peg, no blockchain; Stripe Connect payouts are a later phase. Doctrine: never mint more Current-cy than donation dollars actually held (the float rule).

### Donations
- `donations` (admin-only read + donor-own-read via RLS; service-role writes). Checkout via the `donate-checkout` edge function (through Lichen's own Stripe; `verify_jwt=false` since donors may be signed out). `translate_donation()` mints 95% as Current-cy (context `'grant'`) and records the other 5% as `central_cents` (operating dollars — deliberately never minted). `keep_donation_for_operations()` for general/operations gifts (100% central, mints nothing). `kind` distinguishes `donation` (Lichen decides recipient — deductible) from `sponsorship` (donor picks the recipient — IRS conduit rule, not deductible; the "Give" flow). `inkind_donations` covers non-cash gifts (`accept_inkind_donation()`/`decline_inkind_donation()`, triggers a non-valuing acknowledgment email). `currentcy_float_summary()` is the admin-only float-vs-operating gauge. Auto tax receipts send via Resend from the `stripe-webhook` function, idempotent per donation row.
- `/giving` — an owner-only dashboard of cash + in-kind giving history and the year's deductible total; nobody sees anyone else's giving (same no-counts doctrine as trust).

### Video hosting
- Self-run (not a third-party service): the `videos` storage bucket + a `video_jobs` queue (owner-insert, worker-only advance via service role). `worker/` is a Node+ffmpeg poller producing adaptive HLS (rendition dirs are named `vv0`/`vv1`/… — remember this when listing storage) + a poster image; it runs on the founder's Mac today. `worker/ingest.js` is a local-transcode CLI for large source files, bypassing Supabase's free-tier ~50MB upload cap (only works for videos the founder ingests — other members' large files still need Supabase Pro). `VideoPlayer.tsx` (HLS native on Safari, `hls.js` lazy-loaded elsewhere) is wired into FeedCard.

### Search & maps
- `src/lib/smartSearch.ts` — a deterministic, rule-based sentence interpreter (no AI call): parses trust/recommend degree, price, mode, online/in-person, time windows, place, category, and person names (a trailing name after "recommended by"/"trusted by" sets that filter; otherwise it scopes by author). The full manual criteria panel covers the same ground and merges additively with a typed sentence. Results show near-misses (posts matching *some* but not all terms) below direct hits, never as a silent substitute.
- `src/lib/trustPath.ts` — viewer-relative trust computation (direct trust, or one hop via someone you trust). Powers the marketplace "who you'll do business with" safety lens (Anyone / trusted-by-someone-I-trust / someone-I-trust, `localStorage 'mkt-trust'`) and the mutual-friend trust line shown on cards/tiles.
- Maps (Mapbox, lazy-loaded chunk — keep it lazy, the main bundle stays small): event/space/people pins. `location_shares` (per-location-kind audience rules, most-specific-wins) + `location_level()` resolver — visibility ladder `hidden < state < county < area < exact`; `state` deliberately has no pin (findable-not-pinnable); you always see your own location as exact.

### Notifications & assistant
- `notify()` is the single entry point for every bell (section-scoped: home/profile/calendar/chat/currentcy/membership). `ADMIN_DESK_TYPES` are excluded from the bell UI and unread counts (still written to the DB, still push-delivered) — those surface through each space's own backstage queue instead.
- The assistant is a real Lichen member account (`claude@lichen.health`) plus a per-entity "AI Partner" fabric — two distinct roles, never conflate them in copy. Edge functions: `claude-chat` (legacy 1:1 chat replies, `pg_net` trigger on `chat_messages`), `assistant-feed` (the current door — a member's relationship with Claude as a feed, not a chat thread; `assistant_feed_posts` table, `pg_net` trigger on new member posts there, own daily cap `ASSISTANT_FEED_CAP` default 20/day, `assistant_queries` context `'feed'`), `assistant-search` (narrates search results, context `'search'`), `assistant-brief` (per-section snapshot at `/assistant?section=`, context `'brief'`). `search`/`brief` share `ASSISTANT_DAILY_CAP` (default 30/day); `chat`/`feed` each have their own separate cap — none of the four are pooled together. `AssistantDoor.tsx` is the per-section opt-in/opt-out control (`localStorage 'ai-door-<section>'`) — a section's data is gathered and sent to the assistant **only** when that section's door is on; nothing moves ambiently.
- `assistant_feed_posts` (profile_id, author `'member'|'claude'`, body, source_post_id) is private by construction (RLS = `profile_id = auth.uid()`, no visibility branching) — the pattern to reuse for any future closed 1:1-with-Claude relationship, not `posts` (public/space/mycelium only, no private-pairwise mode). `assistantFeedApi.ts` is the client API; `AssistantComposer.tsx` is the shared text+dictation input (`AssistantBrief.tsx`'s inline reply and the feed's own compose box). "Share to Claude" (a post's `⋯` menu, wired via `FeedCard`'s `extraMenuItems`) sets `source_post_id` so the reply is informed by what was shared, not just the note.
- `profiles.assistant_readable` is the *other* consent direction — whether other members' assistants may read what **you** wrote when briefing them (see Chat above).

## Admin
- `profiles.is_admin = true` gates the admin screens, reached from the Profile page's Admin section (**not** the side menu — the side menu only separates "you" doors from platform doors like Invite/Help/Membership):
  - `/admin/categories` — Review categories (pending category suggestions, approve/reject).
  - `/admin/supporters` — Memberships & gifts (gift/revoke, through-dates, pending invitation-gifts), DonationsDesk (translate a donation into Current-cy + operating dollars), RoutingDesk (entrusted-offering ↔ ISO matches), MintCurrent (admin-only Current-cy issuance).
- SideMenu's **Admin view** toggle (blue-ringed, blue desk-count badges) switches the menu to just the spaces you administer, grouped by kind, each linking straight to its `?manage=1` backstage. `listMyAdminDeskCounts()` counts pending section-shares/join-requests/nesting-proposals per space you admin, duty-scoped and actionable-only (outgoing invites never badge — they're awaiting the invitee, not you).
- Color doctrine: peach = life/engagement, blue = tending the structure — use blue for admin-only affordances (the Manage pill, admin-view badges, the `.is-adminview` primary-button tint).
