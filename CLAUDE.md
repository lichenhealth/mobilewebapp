# Lichen — PWA project guide

Lichen is a holistic-healing nonprofit + conscious-economy platform. This repo
(`lichenhealth/mobilewebapp`, package `lichen-pwa`) is the member-facing PWA.
The founder is non-technical; explain reasoning briefly and prefer small,
reviewable changes. Keep Plan Mode on for anything touching the database or auth.

## Stack & deploy
- React 18 + Vite + TypeScript. Build: `tsc -b && vite build` (it type-checks — always run before considering a change done).
- No package-lock; Vercel runs `npm install`. Vercel auto-deploys `main` on push.
- Backend: Supabase (project `mjqnaevertyzgjlpwynr`). Anon key is hardcoded in `src/lib/supabase.ts` (public by design; RLS protects data).
- DB schema is version-controlled in `supabase/migrations/00000000000000_init.sql` — a `pg_dump --schema-only --schema=public` baseline of the live DB (captured 2026-06-29) plus a manually-appended `auth.users` signup trigger. It's a record/backup, not auto-applied. The live schema is still edited in the Supabase dashboard, so this file can drift — refresh it after DB changes. Tooling: Supabase CLI is linked (`supabase/config.toml`); `pg_dump` lives at `/opt/homebrew/opt/libpq/bin/pg_dump` (no Docker). `supabase db dump`/`db pull` need Docker, which isn't installed — use the direct `pg_dump` against the session pooler instead.
- Marketing site is a separate repo (`lichenhealth/lichen-health`, Astro) — not this one.
- Two domains: **`lichen.healthcare`** = this PWA (DNS on Vercel) · **`lichen.health`** = marketing site (website served by Vercel, but DNS nameservers are still on **Wix** — only the A record was moved, not the nameservers). Transactional email sends from `lichen.healthcare` because Wix can't host the subdomain MX Resend needs. Eventual consolidation onto one domain (for shared login) is an open strategy question.
- Run `tsc -b` and `vite build` locally before committing; fix all type errors (the project builds clean today).

## Conventions
- Design tokens live in `src/styles/tokens.css` (peach accent `--peach`, bone canvas, Archivo body, display serif). Reuse token vars; match existing BEM-ish class names (`.onb__`, `.prof__`, `.cat__`, `.adminc__`, `.conv-row`, `.thread__`).
- Logo: `src/components/LichenMark.tsx`. Icons: `src/components/Icon.tsx` (`<Icon name=... size=... />`).
- Avoid the word "spaces" in member-facing UI — say organizations / communities / groups / places.
- Supabase embeds: when a table has >1 FK to another, disambiguate with the explicit hint, e.g. `profiles!subscriptions_profile_id_fkey(full_name)`. SELF-referencing FKs (spaces.parent_space_id): do NOT embed at all — the FK-NAME hint fails outright ('could not find a relationship between spaces and spaces', PR #57) and the COLUMN hint `spaces!parent_space_id(...)` PARSES but resolves to the CHILDREN direction (an array — rendered ghost 'part of' labels until PR #59). Fetch the parent row explicitly by parent_space_id instead (see spacesApi loadSpaceProfile/listSpacesByKind).
- React hooks must ALL sit above any early return (`if (loading) return …`). A hook added below one crashes the whole app to a blank page when the data arrives ("Rendered more hooks…") — this took out every event page in prod until PR #46 (2026-07-05).
- New enum values can't be USED in the same migration that adds them — add in a separate step that's committed first.
- Only 3 columns use real Postgres enums (`account_capability`, `space_kind`, `space_member_role`). The other "enum-like" fields below (care `status`, subscription `tier`/`source`, category `domain`, suggestion `status`) are actually `text` columns with CHECK constraints — to add a value, change the CHECK, not an enum type.

## Data model (all RLS-enabled)
- `profiles` (id→auth.users; full_name, headline, bio, email, onboarded, is_admin). Trigger creates a profile on signup.
- `profile_capabilities` (service_provider / goods_provider).
- `categories` (63 seeded; text slug id, domain good|service, name, sort) + `profile_categories`. Member-suggested categories via `category_suggestions` + admin approval RPCs `approve_category_suggestion` / `reject_category_suggestion`.
- `spaces` (kind enum: organization|community|group|place; created_by; `parent_space_id` — groups NEST under communities/orgs, nullable = standalone) + `space_members` (role enum: super_admin|admin|member). Creator becomes super_admin via trigger `handle_new_space`. One super_admin per space. MEMBERSHIP IS REQUEST+APPROVAL (2026-07-14, PR #56, migration `20260719120000_space_nesting_requests.sql`): `space_membership_requests` (care-team shape — initiated_by=self → join request admins approve via `approve_join_request()`; =admin → invite accepted via `accept_space_invite()`); NESTING IS CONSENSUAL: `space_nesting_requests` (group admins propose via the Part-of picker or anyone via 'Propose a group' — group is created standalone immediately; parent admins approve via `approve_group_nesting()` or Release later via `eject_group()`; `enforce_parent_consent` trigger blocks non-consensual parent writes). MEMBER SUGGESTIONS (2026-07-14, PR #58, migration `20260720120000_member_suggestions.sql`): any MEMBER may insert a request row for someone else = a SUGGESTION (third INSERT-policy arm); trigger notifies admins only (suggested person hears nothing); admins endorse via `endorse_member_suggestion()` (row's initiated_by becomes the admin → real invite, person notified); `accept_space_invite()` requires the initiator be an admin (a bare suggestion can't be self-accepted). SpaceProfile + circle = an ADD MENU (Post / Marketplace listing / Event via Compose presets / New group (admins) / Propose a group); Members section type-ahead: admins Invite, members Suggest; icons: 'member-heart' (Members) + 'groups' (Groups mark from the Figma icon set). All flows notify via `notify()` (section 'home', space-scoped). Roles are strictly per-space.
- `chats` (one per space — all kinds — and one per care team) + `chat_members` (synced to space_members via trigger) + `chat_messages` (realtime enabled). RLS uses `is_chat_member()` helper to avoid recursion.
- `care_team_members` (patient_id, caregiver_id, status pending|active, initiated_by). Either party initiates; the OTHER approves. Activation trigger creates/join the care-team chat.
- `care_invitations` (invite non-members by email; `claim_care_invitations()` RPC converts them to pending care links on signup).
- `subscriptions` (tier community|concierge, source gift|stripe). Admin RPCs `gift_subscription` / `revoke_subscription`. Stripe columns exist but Stripe is NOT wired yet.

## Real-data architecture (design locked 2026-06-30 — the next major build)
Turning the mock feed/marketplace/mycelium into a real platform. Cornerstone decisions:
- **Members are ENTITIES, not just people.** An entity has a `kind` (person / plant / animal / place / organization). Humans log in; non-humans (e.g. *Tango* the therapy horse, a *San Pedro* cactus) are **stewarded** by a human and act through them. Contributions and value accrue to the *entity itself* (the conscious-economy ledger — a cross-species economy). Today `profiles` = humans (auth-linked). Generalizing `profiles` into multi-species entities (add `kind` + `steward_id`, allow non-auth profiles) is a foundational step; `posts`/`mycelium` are designed to absorb it (an author stays a profile row that *becomes* an entity).
- **Posts = one unified content stream.** Fields: author, optional `space_id`, `visibility` (public/mycelium/space), `content_type` (social/creative/educational/actionable/qa), optional `service_area` (marketplace/work/courses/food/art/events/places/library/people), title/body/image, `details` jsonb (area-specifics: price, schedule, location…).
- **Mycelium = your trusted web.** FOUNDER CLARIFICATION (2026-07-14): mycelium must NOT read as inherently trusted — you may keep someone in your network you work with but don't vouch for, and trust/recommendations stay PRIVATE person-by-person signals so they can't be gamified. Member-facing copy says "someone I trust" / "trusted by someone I trust", never "my mycelium" as a trust degree; never show trust counts/leaderboards. SHIPPED (2026-07-14, PR #54, migration `20260718120000_trust_vouch_split.sql`): mycelium edges carry a PRIVATE `vouched` boolean — membership (web) and trust (vouch) are now SEPARATE gestures. `loadMyWeb()` → {web, vouched}; `setInWeb` (membership only, plain insert ignoring 23505 so it never downgrades a vouch; delete on removal withdraws trust too), `setVouch` (upsert = trusting auto-adds to web; unvouch keeps membership), `setTrust` aliases `setVouch` (feed-card shield = vouch the author). Overlays/search degrees read VOUCHED edges only; /mycelium feed reads the whole WEB. TARGET SPLIT (founder): trust names RELATIONSHIPS (people/org/community/group), recommend points at THINGS (posts/events/products/services/PLACES) — no entity carries both buttons (profiles: Add to Mycelium + Trust; places: Add to Mycelium + Recommend); person/org recommendations were converted to trust edges by the migration; a person's "Recommended by X" in search aggregates from recs of their POSTS. Historically "Trust" and "Add to Mycelium" were the SAME action — a polymorphic edge `you → (target_type, target_id)` over profiles/spaces/posts (eventually any entity). Trusting an entity flows its posts/marketplace items into *your* mycelium feed/marketplace. **Recommend** = amplify a specific post to the people who trust you.
- **Mycelium is a trust LENS over the WHOLE platform.** Everywhere (any community/space), an item's trust/recommend icons highlight (peach/orange) iff someone **in YOUR mycelium** (not that space) trusted/recommended it; hover shows *which of your mycelium members*. Always "what my mycelium endorses," never the broader platform. Quality over quantity. → the endorsement overlay is a query: `(endorsers of item) ∩ (your mycelium)`.
- **Home feed = public ∪ your spaces ∪ content from entities in your mycelium**, narrowed by the content-type chips + service-area lenses. Service-area lenses are **contextual** (in Mycelium they scope to your web; in a space, to that space; on Home, platform-wide).
- **Membership gate**: enforce (active community+ subscription, gift OR paid) at the **RLS level as real data lands** — NOT before (mock content isn't worth gating, and it'd lock out beta). The frontend routing-gate flips LAST. Admins always bypass.

Build order: `posts`/`mycelium`/`recommendations` tables → wire Home feed to real posts → Trust/Recommend + Add-to-Mycelium actions + endorsement overlays → marketplace & other lenses → entity generalization (multi-species + stewardship) → value ledger → membership gate.
